# models/case-study/

SysML v2 models generated by the pipeline for the Continental ZIDA Shield
Operation case study, evaluated across two backbone configurations.

## Evaluation overview (Table I of the paper)

| Metric | Sonnet 4.5 | Haiku 4.5 |
|--------|-----------|-----------|
| SLOC (post-P4 / final) | 3,033 / **3,043** | 3,049 / **2,976** |
| Errors (post-P4 / final) | 35 / **5** | 144 / **14** |
| SLOC error-free (final) | **99.8 %** | **99.6 %** |
| Packages error-free (final) | **25 / 27** | **24 / 27** |
| P5 ⇌ P6 iterations | 1 | 2 |
| Total cost | USD 3.69 | USD 1.26 |
| Total time | 75.0 min | 60.8 min |

## Snapshot definitions

**`post-p4/`** — automated output of P4 RefinementAgent, immediately before the
P5 ValidatorAgent first runs. These files show the pre-validation state and
allow independent reproduction of the error-reduction figures (Δerrors reported
in Table I of the paper).

**`final/`** — final deliverable after (i) the bounded P5 ⇌ P6 automated
correction loop (max. 2 iterations) and (ii) human-in-the-loop review in
SysIDE / Eclipse IDE, as described in §III.C of the paper. These are the
exact files on which the Table I and Table II metrics were computed.

## Human-in-the-loop review scope

The paper's evaluation pipeline (Fig. 1) ends with a human review stage.
For each backbone, a domain expert inspected the automated P5 validation
report in SysIDE (textual editor) and Eclipse IDE (graphical view) and
applied targeted corrections to the residual issues classified as
`KNOWN_LIMITATION` by the P5 LimitationDetector (rules L01–L04). These
corrections are reflected in `final/` but not in the automated P5 validation
report produced by the pipeline, which captures the automated output only. That
report is not committed; it can be regenerated by re-running the system.
